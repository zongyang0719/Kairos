# Kairos

> 过去的软件是仓库，人是管理员；Kairos 把管理员换成 Being，人退到只剩拍板。

一个 Mac 上的账本，背后站着一个替你记、替你理、替你跟的 being。你只做两件事：理解、拍板。手机端可选伴侣，iCloud 同步是可选能力，各自都能单机跑。

它用 AI 重做「日程管理」——重做的不是界面，是**谁替你记、谁替你理、谁替你判断**这三件事的重新分配。过去几十年的生产力软件共享同一个隐藏假设：人负责记，软件负责存。Todo、日历、笔记、看板都只是诚实的仓库。AI 第一次让分工可以反过来。

## 为什么先做日程

它是这个分工反转的**最小完整闭环**——信息进来 → 判断 → 行动 → 沉淀——每个人每天都在跑。人不缺工具，缺的是「现在真正重要的是什么」没有任何一个工具在回答。够小、够日常、够痛。

Kairos 是希腊语的「对的时机」，对应 chronos「钟表时间」。软件催人做人自己记下的事，是旧范式残留；Being 知道时机、替人把握时机，才是这个名字的本义。

## 痛点在哪

待办和日程这个品类做了二十年、上千个产品，而今天大多数人真正在用的是「发给自己的一条微信」。
不是竞争饱和，是**所有产品都在服务愿意做结构化劳动的那一小撮人**，其余人退回了最原始的手段。

病根只有一条：**它们都要求人自己录入、自己排序、自己维护。** 具体的毛病全是它的副作用——

- **填着累，所以不填。** 填得越全（截止日、优先级、标签、项目）系统越能帮你，可成本也越高。结局只有两种：空的漂亮 app，或者一个垃圾堆。
- **只进不出，所以烂掉。** 录入率永远高于完成率，清单是个只涨的堆。打开它变成一种羞耻体验。GTD 的补丁是「每周回顾」——要求人定期主动面对自己的失败清单。
- **优先级是假的。** P0/P1/高中低用三周一定全塌成一档。优先级不是一个属性，是**比较**，而且只在「此刻、我有这么多时间、这些人在等」的语境下才成立。静态字段表达不了它，只能表达焦虑。
- **状态在别处。** 那条「回复张三」真正的状态活在聊天软件里、在张三脑子里。清单上那条只是影子，影子不会自己更新。

二十年没人解决，不是设计不够好——Things 已经把界面那条路走到了物理极限，你的清单照样会烂。
是因为在 LLM 之前，这几条**在计算上不可解**：机器不懂人话，就只能要求你填表；不懂上下文，就只能要求你手工同步；没有判断力，就只能要求你自己排序。
所有待办软件本质上是**把人当数据录入员和调度器的界面**。

**但这不等于自动排程。** 过去两年的 AI 日历产品大多死在同一个地方：人肉 time blocking 很累，
于是它们帮你自动 time blocking。可问题从来不是排得慢，是**排这件事本身是错的**——
把只对自己负责的意图，伪装成有对手方的承诺，然后被现实打脸，然后重排。自动化那一步只是让打脸来得更快。
Kairos 自动化的是另一段劳动：记、理、判断、盯。

## 产品判断（已定）

**一条待办只有一个状态维度。** 走到哪了，完没完，都是它。「谁在办」不是字段（`owner` 撤了，两端没有一块屏幕画过它）——要说谁在办，在这条的房间里说一句。

**顺序是 Being 排的。** 单子就是账本里 `items` 的次序，界面从上往下画，没有 rank 字段。`tier` 只管红点，不管顺序。

```
todo     未开始（默认）
doing    进行中——being 或你正在推，不允许长期停在这儿
pending  待定——卡着等别人、等信息、等时机
closed   已完结，结论沉淀成判例，抽屉不占屏
```

**完成不用你回来打勾。** 做完了再回 app 点一下，是最容易漏的一步，清单失真全从这来。
应该由 being 从证据推断（信发出去了、对方回了、文件提交了），**人只负责否认**。
这条不是新想法——契约里早写着「追踪人回没回是噪音，还会逼人回来点『已回复』」，
只是以前没推到底：**了结也是同一种劳动**。

**活着要拿证据。** 清单只增不减是这个品类烂掉的同一个死因。所以默认反过来：
**留着要给理由，不是删掉要给理由。** 一条每次在任何渠道被提到就追加一条真源；
超过两周没有新证据的，being 自己把它往下排，排到你不会再看见的位置。不需要每周回顾。

**可逆的全自动，不可逆的拿证据。** 分级的判据不是「重不重要」——那个每次都得重新想，
而且想得越久越倾向于打扰人；是**这一下撤不撤得回来**。排序、归项目、补背景、调档位，
being 不问就做；了结撤不回来，所以完成判断拿证据说话——**确实完成了，being 直接替你勾掉**，勾错了说一声、重开回 `todo`；真正必须问你的只剩两件：删除、对外发消息。

**时间下沉。** 不做 due date、不做时间轴、不做逾期提醒。时间没有消失，是沉进了 being 的记忆层：周五要交的东西周四浮到列顶，而不是看板上挂一个红色「已逾期」。没做完的事停在原地，不催、不红。

**清 inbox 是 being 的活。** 新信号默认落到 being 手上，消化完才允许进 `mine`。一条进 `mine` 必须带齐入场券：是什么（summary）、消化过的背景（brief）、为什么现在找你（reason）、要判断什么（ask）。填不齐的轮不到你看。**看板越薄越对**——薄是证据，证明 being 扛住了。

**秘书模式，不是客服模式。** being 以回合异步工作，不是坐在页面里等消息的聊天框。你看到的是它干完活留下的结果和留言。

## 架构

```
  人类 ────── Loom ────── being （being）────── Town（别的 being）
   │
  Kairos
```

五点，展开在 [ARCHITECTURE.md](ARCHITECTURE.md)：

1. **每条待办一个对话房间。** session_id 就是房间号。「订体检」的来回不污染「报税」的对话。
2. **文件是真源，消息是通知。** 账本是那一个 json 文件；房间是过程记录，整个删掉账本也不少东西。
3. **五句规则管账本怎么写。** 锁全程、手动改不被覆盖、快照落盘、先文件后消息、未读分两级。
4. **三条通道各自房间，互不串。** 说话和通知进待办的房间；账本有专用的一间，进不了主对话。
5. **手机够不着 Town，being 代跑。** Town 的 DM 只认 being 的 Heart，手机直接打过去是 401。手机把要发的信托给 being，being 跑一趟，只回一个 json 块。

这和 [BeingDesktop](https://github.com/GuangCZ/BeingDesktop) 的多会话是同一个方案——服务端不认房间，客户端自己记账。它证明了这条路不用改服务端就能跑。

## 现在跑到哪了

**Mac 和 iPhone 各自都能单机跑，iCloud 是可选的关联。**

- **单机（默认）**：账本就在这台机器上——Mac 在 `~/.kairos/projection-snapshot.json`，iPhone 在「文件」App → 我的 iPhone → Kairos 里。不登 iCloud 照常用，整个配置只有一件事：粘一条 loom 链接。
- **关联（可选）**：两边都指到 iCloud 云盘里同一个 `Kairos` 文件夹。规则不变——账本只有 Mac / being 写，手机写自己的 `outbox/<设备>.json`，Mac 打开时收进来。**不是多端共写同一个文件**——iCloud 是文件同步器不是服务器，没有锁也不合并，多端平等共写同一份账本必然互相踩（原理见 ARCHITECTURE.md）。
- **换位置不丢东西**：设置里换，两边的账本先按 id 并起来，并之前两份都备份到 `~/.kairos/backups/`。手机接上时，单机期间攒的条目会排队等 Mac 收进共享账本。

能做的：建待办、改待办、在每条待办的房间里跟 being 说话、请它看一眼账本补背景。Mac 上 being 还能直接跑 `ledger/cli.js` 读写账本（位置它自己解析，不用你告诉它）。

## 跑起来

**下载安装（推荐）**：到 [Releases](https://github.com/zongyang0719/Kairos/releases) 下载最新 `Kairos-*.zip`（如 `Kairos-v2.5.2-macOS.zip`），解压，把 Kairos.app 拖进「应用程序」。

首次打开：当前版本尚未做 Apple 公证，第一次打开可能被系统拦截。在终端跑一次：

```bash
xattr -cr /Applications/Kairos.app
```

> 若双击报「应用程序无法打开」（非「已损坏」）：终端跑 `chmod +x /Applications/Kairos.app/Contents/MacOS/kairos` 后再开——个别解压工具会丢执行位。

之后正常打开。

**从源码构建**

**iPhone**：Xcode 打开 `KairosiOS.xcodeproj`，数据线插手机，⌘R。装完点单子右上角那颗头像（「我」），粘 loom 链接。

**测试**：测试代码在开发仓，不随公开快照分发。

**Mac**：`./build-kairos.sh`，编完直接装进 /Applications。边栏是项目和存下来的视图；一张待办列表，按优先级或状态分组、也可以不分组；点一条右侧出这条的房间。

## 数据与卸载（生命周期）

**数据都在哪**：

| 数据 | 位置 | 卸载 app 后 |
|---|---|---|
| 账本（待办、真源） | 你选的文件夹（默认 iCloud 的 Kairos） | 保留 |
| 连接信息（API 链接、token） | `~/.kairos/connection.json` | 保留 |
| 窗口尺寸、草稿等偏好 | UserDefaults | 保留（无害） |

**卸载不会丢数据**：删掉 app 本体，账本原地不动。重装后接到同一个文件夹，一切照旧——账本不属于 app，属于你。

**想彻底清除**（先确认不需要了）：

```bash
rm -rf ~/.kairos          # 连接信息、锁文件（含 token，敏感）＋历史备份与投影快照
```

注意：这条命令除了连接信息，还会删掉 `~/.kairos/backups/`（账本历史备份）和投影快照。主账本在你选的文件夹（iCloud）不受影响；但如果想留备份，先拷走 `~/.kairos/backups/` 再执行。只断开连接不删备份：用 设置 → Being → 「断开连接」。

账本文件夹（iCloud 里的 Kairos）自己删。**与 being 断开**：设置 → Being → 「断开连接」——只删本机连接信息，账本不动，重填链接即恢复。
